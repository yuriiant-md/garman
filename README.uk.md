# Гарман

[English](README.md) · Українська

Telegram-бот для фермера: витягує умови з договору трейдера, знаходить ризики з посиланням на пункт договору чи норму закону й допомагає порівнювати пропозиції. Курсовий проєкт розвивається поетапно; етап 1 готовий до перевірки: витягування умов угоди з «брудних» текстів і порівняння платних моделей з локальною.

Етап 1 проганяли двічі. Перша матриця порівнювала Claude Haiku 4.5 з локальною Lapa 12B; Lapa дала близько 27% точності заповнених полів на реальних договорах, тож на етапі 1.2 її замінили на Qwen3 14B і додали GPT-4o через OpenRouter як другу платну модель. `make run` тепер проганяє матрицю етапу 1.2 у `results/stage1_2/`; перша матриця лишається в `results/stage1/`, і `make metrics` читає її з `--results-dir` (крок 4).

## Як відтворити етап 1

### Що потрібно

- macOS або Linux з `make` і [uv](https://docs.astral.sh/uv/getting-started/installation/). Python 3.14 uv встановить сам під час першого `make install`.
- Щоб відтворити наші цифри (крок 3), **потрібні** ключ Anthropic API для Claude Haiku 4.5, ключ [OpenRouter](https://openrouter.ai) для GPT-4o і [Ollama](https://ollama.com) з Qwen3 14B (завантаження 9,3 ГБ, під час роботи — близько 12 ГБ вільної пам'яті). Без них працюють лише кроки 1, 2 і 4: встановлення, юніт-тести й перегляд збережених прогонів.

### Команди make

| Команда | Що робить | Потрібні ключ і Ollama |
| --- | --- | --- |
| `make install` | встановлює залежності (`uv sync`) | ні |
| `make test` | юніт-тести на підставних моделях: офлайн, кілька секунд; перевіряють код, а не якість моделей | ні |
| `make smoke` | швидка жива перевірка: 12 конфігурацій на перших 2 текстах кожного джерела (6 текстів), результат у `results/smoke/<час початку>/`; близько $1 і 20 хвилин | так |
| `make run` | повний живий прогін: 12 конфігурацій на всіх 37 текстах, результат у `results/stage1_2/<час початку>/` разом із двома таблицями метрик; близько $5 і 1,5 години | так |
| `make metrics` | друкує таблицю метрик останньої збереженої папки в `results/stage1_2/`; не звертається до моделей і нічого не записує | ні |

### 1. Встановити

```bash
git clone <repository-url> garman
cd garman
make install    # = uv sync
```

### 2. Перевірити

```bash
make test       # = uv run pytest -q
```

Тести працюють офлайн за кілька секунд на підставних моделях: без ключа API, без Ollama, без мережі. Вони перевіряють код (розбір, валідацію, спробу виправлення, арифметику метрик), а не якість моделей — цифри дає крок 3.

### 3. Запустити етап 1

```bash
cp .env.example .env    # впиши свої ключі: ANTHROPIC_API_KEY=... і OPENROUTER_API_KEY=...
ollama pull qwen3:14b
make run        # = uv run --env-file .env python main.py
```

`make run` запитує моделі для кожної конфігурації етапу 1.2 на всіх 37 текстах — 3 моделі (Claude Haiku 4.5, GPT-4o, Qwen3 14B) × 2 промпти × 2 семплінги (`precise`, `varied`) = 12 конфігурацій. Кешу немає: кожен прогін робить живі виклики API й Ollama. Наш повний прогін коштував $5 ($1,8 за Claude, $3,2 за GPT-4o) і тривав близько 1,5 години на Mac з Apple Silicon: 10 хвилин Claude, 6 — GPT-4o і 80 — Qwen. Цифри трохи відрізняються від прогону до прогону: платні моделі не повністю детерміновані навіть при temperature 0, а промпт v2 містить дату запуску (`{today}`).

GPT-4o отримує схему як строгий structured output (`response_format` зі `strict: true`), тож не може відповісти поза нею; Claude отримує її як обов'язковий виклик інструмента, який API не компілює строго для схеми такого розміру. OpenAI оголосила GPT-4o застарілою, тож тут вона — точка порівняння, а не кандидат у продакшн.

Кожен запуск зберігається в нову папку з назвою за часом початку, наприклад `results/stage1_2/2026-10-27T14-05-33/`. У ній по одному файлу на конфігурацію з іменем із моделі, версії промпту й семплінгу (`claude-haiku-4-5__v2__precise.jsonl`, `openai_gpt-4o__v2__precise.jsonl`; у кожному рядку є також `run_at`) і дві таблиці, побудовані з них: `metrics.md` та `metrics_by_field.md` (точність і вигадані значення по кожному полю й конфігурації, на test golden set). Попередні папки ніколи не змінюються, тож запуски можна порівнювати папка з папкою.

Конфігурацію, якій потрібна відсутня модель (немає ключа в `.env`, не запущено Ollama), пропущено з поясненням; решта все одно проганяється, а `make run` завершується з кодом 1 і переліком того, що не завершено.

Для швидкої перевірки є `make smoke` (= `python main.py --per-source 2`): ті самі 12 конфігурацій на перших 2 текстах кожного джерела (6 текстів), близько $1 і 20 хвилин, здебільшого через Qwen. Результат іде в `results/smoke/<час початку>/`, який git ігнорує, а `make metrics` не читає. Цифри на 6 текстах нічого не доводять — це лише перевірка, що все працює разом. Запусти її перед повним прогоном, щоб побачити, що ключі, Ollama і весь ланцюжок працюють.

### 4. Переглянути збережені прогони

```bash
make metrics    # = uv run python -m src.extraction.metrics
```

Це лише перечитує вже збережені результати, тож не потребує ні ключа API, ні Ollama — саме по собі воно нічого не відтворює, цифри дає крок 3. Команда порівнює збережені прогони з останньої папки в `results/stage1_2/` з еталонною розміткою й друкує таблицю метрик (нічого не записується, тож збережена таблиця потім не змінюється). Іншу папку вибери так: `--results-dir <папка>`; щоб записати таблиці, додай `--output <файл> --by-field-output <файл>`. Щоб порівняти свій прогін із нашим, наш прогін етапу 1.2 лежить у `results/stage1_2/2026-10-24T18-41-35/`. Перша матриця етапу 1 (Claude і Lapa, 8 конфігурацій) лежить у `results/stage1/2026-10-23T11-46-35/` (`2026-10-23T10-56-10/` — попередній прогін на 4 конфігурації лише з семплінгом `precise`):

```bash
uv run python -m src.extraction.metrics --results-dir results/stage1/2026-10-23T11-46-35
```

### Окремі команди

```bash
uv run --env-file .env python -m src.extraction.run --split all                 # одна конфігурація: Claude, промпт v2, precise
uv run --env-file .env python -m src.extraction.run --model gpt --split all     # GPT-4o, промпт v2, precise
uv run python -m src.extraction.run --model qwen --prompt prompts/extract_v1.md   # Qwen, промпт v1, тексти dev
uv run python -m src.extraction.metrics                                          # лише таблиця метрик (= make metrics)
uv run python -m scripts.check_golden                                            # перевірка розмітки golden set
```

`--split` — `dev` (синтетичні тексти), `test` (golden set) або `all`; `--sampling` — назва з `configs/sampling.yaml`. Кожен прогін зберігається в новий файл, жоден не використовується повторно.

Підготовка golden set із договорів Prozorro (докладно — у `data/README.md`):

```bash
uv run python -m scripts.fetch_prozorro    # кандидати в data/raw/prozorro_candidates/
uv run python -m scripts.pdf_to_text       # data/raw/prozorro/*.pdf → data/texts/prozorro_NNN.txt
```

## Як рахуються метрики

Правила записані до першого прогону; код — `src/extraction/scoring.py` (один документ) і `src/extraction/metrics.py` (таблиця), кожне правило має свій тест у `tests/test_scoring.py` і `tests/test_metrics.py`.

1. **Одиниця — кінцеве поле** угоди (`price.amount_per_t`, `payment.trigger`). Порожній вкладений об'єкт дорівнює об'єкту, де всі поля `null`. Поле `delivery.period_raw` не рахується.
2. **Порівняння:** enum, bool і дати — точний збіг; числа — до сотої (9200 = 9200.004, але 0.1 ≠ 0.11); рядки — після нормалізації (регістр, лапки, апострофи, правова форма ТОВ, ТзОВ, ПрАТ, АТ, ДП, ПП, ФГ) і зі схожістю ≥ 0.85 (`difflib`). Поріг підібрано на OCR-шумі golden Prozorro: виправлена моделлю назва дає 0.87–0.99, назва в іншому відмінку — 0.82, латиницею — 0. Відома вада: назви, що відрізняються лише цифрою, теж зараховуються.
3. **Неустойки** спарюються за (`payer`, `trigger`, `unit`) незалежно від порядку; із кількох кандидатів береться той, що збігається з еталоном за більшою кількістю з `amount` і `cap_pct`. Неустойка без пари — усі її поля хибні; зайва — її значення вигадані.
4. **Три числа замість одного:** точність заповнених — головна, лише поля, що в еталоні не `null`; вигадані, % — модель дала значення там, де в еталоні `null`; загальна — усі поля, для довідки. Інакше відповідь «усе `null`» мала б високий бал. Точність рахується по сумі полів усіх документів.
5. **Провальна відповідь** (`failed` чи `error`) не викидається: усі її поля хибні, а порожні в еталоні поля рахуються вигаданими, щоб збій не виглядав кращим за помилку.
6. **Валідність** — окремо: валідні, failed і «виправлені» — частка документів, що стали валідними лише після однієї спроби виправлення (вона входить у валідні, а не в failed).
7. **`varied`** біжить один раз за запуск, як і `precise`, тож його розкид видно лише порівнянням запусків; 3 повтори на golden із середнім і розкидом заплановано на фінальний прогін.
8. **Окремо по наборах:** синтетика (dev), Prozorro і власні договори (test); модель обирається за всіма golden разом.
9. **Шум:** до точності заповнених додається 95% бутстреп-інтервал — 1000 вибірок документів із поверненням, фіксований seed. Якщо інтервали двох конфігурацій перетинаються, перевагу не заявляю.
10. **Вартість** — токени всіх спроб × тариф із `configs/models.yaml`, на 1000 відповідей без `error`; для локальних моделей — $0.
