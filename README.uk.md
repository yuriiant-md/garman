# Гарман

[English](README.md) · Українська

Telegram-бот для фермера: витягує умови з договору трейдера, знаходить ризики з посиланням на пункт договору чи норму закону й допомагає порівнювати пропозиції. Курсовий проєкт розвивається поетапно; етап 1 готовий до перевірки: витягування умов угоди з «брудних» текстів і порівняння платних моделей з локальною.

Етап 1 зростав у три кроки. Перша матриця порівнювала Claude Haiku 4.5 з локальною Lapa 12B; Lapa дала близько 27% точності заповнених полів на реальних договорах, тож на етапі 1.2 її замінили на Qwen3 14B і додали GPT-4o через OpenRouter як другу платну модель. Етап 1.3 змінив схему: договір може називати кілька класів, кожен зі своєю ціною за тонну й своїми показниками якості (натура, клейковина, число падіння, …), і додав Claude Haiku 5.5, яка стала основною моделлю (`REPORT.md`, розділ 6). З етапу 1.3 локальної моделі в коді немає: курс її більше не вимагає, а локальні прогони лишаються в `results/` для історії. `make run` тепер проганяє матрицю етапу 1.3 у `results/stage1_3/`. Попередні матриці лишаються в `results/stage1/` і `results/stage1_2/`; їх рахували за схемою до класів, тож перечитують їх кодом тегу `stage-1` (крок 4).

Етап 2, RAG із посиланнями на джерело, у роботі: корпус, чанки, пошук, відповіді з джерелами та їхня перевірка правилами й LLM-суддею готові (розділи «Як документи діляться на чанки», «Як працює пошук», «Як працюють відповіді» і «Як перевіряються відповіді» нижче). Суддю відкалібровано на ручних оцінках автора: він збігається з ними в 95% перевірок correct і 85% тверджень (потрібно 80%).

## Як відтворити етап 1

### Що потрібно

- macOS або Linux з `make` і [uv](https://docs.astral.sh/uv/getting-started/installation/). Python 3.14 uv встановить сам під час першого `make install`.
- Щоб відтворити наші цифри (крок 3), **потрібні** ключ Anthropic API для Claude Haiku 5.5 і 4.5 та ключ [OpenRouter](https://openrouter.ai) для GPT-4o. Без них працюють лише кроки 1, 2 і 4: встановлення, юніт-тести й перегляд збережених прогонів.

### Команди make

| Команда | Що робить | Потрібен ключ |
| --- | --- | --- |
| `make install` | встановлює залежності (`uv sync`) | ні |
| `make test` | юніт-тести на підставних моделях: офлайн, кілька секунд; перевіряють код, а не якість моделей | ні |
| `make smoke` | швидка жива перевірка: 10 конфігурацій на перших 2 текстах кожного джерела (6 текстів), результат у `results/smoke/<час початку>/`; близько $1,6 і 8 хвилин | так |
| `make run` | повний живий прогін: 10 конфігурацій на всіх 48 текстах, результат у `results/stage1_3/<час початку>/` разом із двома таблицями метрик; близько $12 і 50 хвилин запитів (наш прогін етапу 1.3 — $11,9) | так |
| `make metrics` | друкує таблицю метрик останньої збереженої папки в `results/stage1_3/`; не звертається до моделей і нічого не записує | ні |

### 1. Встановити

```bash
git clone <repository-url> garman
cd garman
make install    # = uv sync
```

### 2. Перевірити

```bash
make test       # = uv run pytest -q
```

Тести працюють офлайн за кілька секунд на підставних моделях: без ключа API, без мережі. Вони перевіряють код (розбір, валідацію, спробу виправлення, арифметику метрик), а не якість моделей — цифри дає крок 3.

### 3. Запустити етап 1

```bash
cp .env.example .env    # впиши свої ключі: ANTHROPIC_API_KEY=... і OPENROUTER_API_KEY=...
make run        # = uv run --env-file .env python main.py
```

`make run` запитує моделі для кожної конфігурації етапу 1.3 на всіх 48 текстах — основна модель Claude Haiku 5.5 × 2 промпти із семплінгом `default`, а також дві моделі, з якими її порівнюємо (Claude Haiku 4.5, GPT-4o), × 2 промпти × 2 семплінги (`precise`, `varied`) = 10 конфігурацій. Haiku 5.5 відхиляє будь-які temperature і top_p, крім власних, тож не отримує ні `precise`, ні `varied`: `default` не надсилає жодних параметрів семплінгу. Кешу немає: кожен прогін робить живі виклики API. Повний прогін етапу 1.2 (12 конфігурацій) коштував $5 ($1,8 за Claude Haiku 4.5, $3,2 за GPT-4o) і тривав близько 1,5 години на Mac з Apple Silicon: 10 хвилин Claude, 6 — GPT-4o і 80 — Qwen. Прогін етапу 1.3 (ті самі 10 конфігурацій на 48 текстах) коштував $11,9 ($4,1 за Claude Haiku 4.5, $0,19 за Claude Haiku 5.5, $7,7 за GPT-4o) і зайняв близько 50 хвилин запитів: 23 — Haiku 4.5, 20 — GPT-4o, 6 — Haiku 5.5. Цифри трохи відрізняються від прогону до прогону: платні моделі не повністю детерміновані навіть при temperature 0, а промпт v2 містить дату запуску (`{today}`).

Щоб запустити лише частину моделей, назви їх у `--models`; ключі — це назви моделей: `haiku-5.5` (основна), `haiku-4.5`, `gpt-4o`. Це секції `configs/models.yaml`, тож нова секція — новий ключ. `uv run --env-file .env python main.py --models haiku-5.5` проганяє лише основну модель: 2 конфігурації, близько $0,2 і 6 хвилин. `--models` працює і разом із `--per-source` (нижче).

GPT-4o отримує схему як строгий structured output (`response_format` зі `strict: true`), тож не може відповісти поза нею; обидві моделі Claude отримують її як обов'язковий виклик інструмента, який API не компілює строго для схеми такого розміру. OpenAI оголосила GPT-4o застарілою, тож тут вона — точка порівняння, а не кандидат у продакшн.

Кожен запуск зберігається в нову папку з назвою за часом початку, наприклад `results/stage1_3/2026-10-27T14-05-33/`. У ній по одному файлу на конфігурацію з іменем із моделі, версії промпту й семплінгу (`claude-haiku-4-5__v2__precise.jsonl`, `claude-haiku-5-5__v2__default.jsonl`, `openai_gpt-4o__v2__precise.jsonl`; у кожному рядку є також `run_at`) і дві таблиці, побудовані з них: `metrics.md` та `metrics_by_field.md` (точність, вигадані значення й зайві елементи списків по кожному полю й конфігурації, на test golden set). Попередні папки ніколи не змінюються, тож запуски можна порівнювати папка з папкою. Файл результатів теж ніколи не перезаписується: повторний запуск тієї самої моделі, версії промпту й семплінгу в ту саму папку зупиняється з повідомленням, тож новому промпту потрібна власна версія в шапці (лише латинські літери, цифри, `.`, `_` і `-`, бо версія входить в ім'я файлу).

Конфігурацію, якій потрібна відсутня модель (немає ключа в `.env`), пропущено з поясненням; решта все одно проганяється, а `make run` завершується з кодом 1 і переліком того, що не завершено.

Для швидкої перевірки є `make smoke` (= `python main.py --per-source 2`): ті самі 10 конфігурацій на перших 2 текстах кожного джерела (6 текстів), близько $1,6 і 8 хвилин. Результат іде в `results/smoke/<час початку>/`, який git ігнорує, а `make metrics` не читає. Цифри на 6 текстах нічого не доводять — це лише перевірка, що все працює разом. Запусти її перед повним прогоном, щоб побачити, що ключі й весь ланцюжок працюють.

### 4. Переглянути збережені прогони

```bash
make metrics    # = uv run python -m src.extraction.metrics
```

Це лише перечитує вже збережені результати, тож не потребує ключа API — саме по собі воно нічого не відтворює, цифри дає крок 3. Команда порівнює збережені прогони з останньої папки в `results/stage1_3/` з еталонною розміткою й друкує таблицю метрик (нічого не записується, тож збережена таблиця потім не змінюється). Іншу папку вибери так: `--results-dir <папка>`; щоб записати таблиці, додай `--output <файл> --by-field-output <файл>`. Повний прогін етапу 1.3 — 10 конфігурацій Claude Haiku 4.5, Claude Haiku 5.5 і GPT-4o, без локальної моделі, — лежить у `results/stage1_3/2026-10-26T16-10-58/` (`REPORT.md`, розділ 5); перший, лише Claude Haiku 5.5, — у `results/stage1_3/2026-10-25T13-25-34/`.

Попередні матриці рахували за схемою до класів. Їхні відповіді тримають ціну за тонну в `price`, а клас і показники якості — в `quality`; цих полів у поточній схемі вже немає, тож поточний код читає їх як порожні й рахує хибними. Перечитуй їх кодом тегу `stage-1`. Наш прогін етапу 1.2 лежить у `results/stage1_2/2026-10-24T18-41-35/`; перша матриця (Claude і Lapa, 8 конфігурацій) — у `results/stage1/2026-10-23T11-46-35/` (`2026-10-23T10-56-10/` — попередній прогін на 4 конфігурації лише з семплінгом `precise`):

## Як рахуються метрики

Правила записані до першого прогону (правила для класів і показників якості додано на етапі 1.3); код — `src/extraction/scoring.py` (один документ) і `src/extraction/metrics.py` (таблиця), кожне правило має свій тест у `tests/test_scoring.py` і `tests/test_metrics.py`.

1. **Одиниця — кінцеве поле** угоди (`grades.amount_per_t`, `payment.trigger`); показник якості — одна одиниця цілком (правило 3). Порожній вкладений об'єкт дорівнює об'єкту, де всі поля `null`. Поле `delivery.period_raw` не рахується.
2. **Порівняння:** enum, bool і дати — точний збіг; числа — до сотої (9200 = 9200.004, але 0.1 ≠ 0.11); рядки — після нормалізації (регістр, лапки, апострофи, правова форма ТОВ, ТзОВ, ПрАТ, АТ, ДП, ПП, ФГ) і зі схожістю ≥ 0.85 (`difflib`). Поріг підібрано на OCR-шумі golden Prozorro: виправлена моделлю назва дає 0.87–0.99, назва в іншому відмінку — 0.82, латиницею — 0. Відома вада: назви, що відрізняються лише цифрою, теж зараховуються.
3. **Елементи списків спершу спарюються**, незалежно від порядку: неустойки — за (`payer`, `trigger`, `unit`), класи — за назвою класу (`grade`, точний збіг), показники якості — за назвою й межею (`min`/`max`); показнику `other` потрібна ще й схожа записана назва, яку порівнюють без пояснення в закритих дужках після неї. Із кількох кандидатів береться той, що збігається з еталоном за більшою кількістю решти значень (`amount` і `cap_pct`; ціна за тонну; значення й одиниця). Показник якості — одна одиниця, `grades.indicators.<назва>`, правильна, коли збігаються і значення, і одиниця. Елемент еталону без пари — усі його поля хибні; клас без пари — хибні його ціна й кожен показник. Зайвий елемент, якого немає в еталоні, — одна хибна одиниця загальної точності, і рахується він в окремій колонці «Зайві елементи»: він не входить ні в головну точність (лише поля еталону), ні у вигадані (його значення не стоять там, де в еталоні `null`).
4. **Три числа замість одного:** точність заповнених — головна, лише поля, що в еталоні не `null`; вигадані, % — модель дала значення там, де в еталоні `null`; загальна — усі поля, для довідки. Інакше відповідь «усе `null`» мала б високий бал. Точність рахується по сумі полів усіх документів.
5. **Провальна відповідь** (`failed` чи `error`) не викидається: усі її поля хибні, а порожні в еталоні поля рахуються вигаданими, щоб збій не виглядав кращим за помилку.
6. **Валідність** — окремо: валідні, failed і «виправлені» — частка документів, що стали валідними лише після однієї спроби виправлення (вона входить у валідні, а не в failed).
7. **`varied`** біжить один раз за запуск, як і `precise`, тож його розкид видно лише порівнянням запусків; 3 повтори на golden із середнім і розкидом заплановано на фінальний прогін.
8. **Окремо по наборах:** синтетика (dev), Prozorro і власні договори (test); модель обирається за всіма golden разом.
9. **Шум:** до точності заповнених додається 95% бутстреп-інтервал — 1000 вибірок документів із поверненням, фіксований seed. Якщо інтервали двох конфігурацій перетинаються, перевагу не заявляю.
10. **Вартість** — токени всіх спроб × тариф із `configs/models.yaml`, на 1000 відповідей без `error`; для локальних моделей — $0.

## Як документи діляться на чанки (етап 2)

`uv run python -m scripts.chunk_rag` (локально, безплатно, кілька секунд) перетворює `data/rag/documents.jsonl` на `data/rag/chunks.jsonl`, один чанк на рядок; повторний запуск записує ті самі байти. Чанки йдуть за структурою документа, а не за фіксованою кількістю символів, бо відповідь має послатися на місце, яке людина знайде: [own_003, п. 7.3], [ЦК, ст. 625]. Код — `src/rag/structure.py` (на що відповідь може послатися) і `src/rag/chunking.py` (розміри й метадані); тести — `tests/test_rag_structure.py`, `tests/test_chunking.py`, `tests/test_chunk_rag.py`.

1. **Одиниця — те, на що посилається відповідь.** Договір ділиться на преамбулу, пункти «7.3» і реквізити. Пункт починається лише там, де його номер зростає, тож перенесене всередині п. 3.1 «1.1 цього Договору» нового пункту не відкриває. Рядок розділу «5. Ціна» рахується, лише коли наступний пункт — 5.x, а все після останнього пункту, що схоже на назву сторони чи реквізити, іде в розділ «Реквізити та додатки». Закон ділиться на цілі статті «ст. 625». Постанова — на абзаци «п. 5.12»; її розділи — заголовки великими літерами («ВСТАНОВИВ:») і рядки «N. Назва». Рядки розділів і заголовків не входять у текст чанка: вони лишаються в його метаданих.
2. **Межі: не більше 1500 символів, зливати коротші за 200.** Їх узято з самого корпусу: пункти договорів мають медіану 300 символів, p90 — 1175, і 106 з 1777 довші за 1500; статті законів — медіану 584; абзаци постанов — медіану 411, p90 — 1677. Тож 1500 зберігає цілими 94% пунктів і майже кожну статтю. За токенізатором bge-m3 тексти в індексі (назва, розділ, заголовок і текст) мають медіану 147 токенів, p90 — 316 і щонайбільше 544: набагато менше за 8192, які приймають bge-m3 і reranker, тож нічого не обрізається.
3. **Довга одиниця спершу ділиться за власною нумерацією:** пункт — на підпункти «п. 10.6.1», стаття — на частини «ст. 30, ч. 1» або пункти ПКУ «ст. 201, п. 201.1». Що все одно задовге, ділиться між рядками, далі між реченнями, далі між словами, і кожен шматок зберігає посилання своєї одиниці.
4. **Коротка одиниця** (менше 200 символів, як «1.1. Товар — пшениця.») приєднується до сусідньої, коли обидві в одному розділі чи статті й разом вміщуються в 1500; посилання стає діапазоном «п. 1.1–1.3» або переліком «преамбула, п. 1.1». Одиниці від 200 символів лишаються по одній у чанку, тож їхні посилання точні.
5. **Кожен чанк несе** `chunk_id` (`own_001#007`), `doc_id`, тип, назву, коротку назву для цитування, URL джерела, дату редакції, `in_force`, `cites_commercial_code`, хеш тексту документа (змінився документ — його чанки застаріли), розділ, заголовок, посилання й сторінки.
6. **Порівняння з чанками фіксованого розміру.** Базовий варіант — вікна по 1500 символів із перекриттям 200 по тому самому тексту документа, виміряні на тих самих одиницях. *Розрізані пункти*: одиниці з посиланням, які жоден чанк не містить цілком. *Перетин меж*: чанки, що зачіпають два розділи договору або дві статті закону. *Одне посилання*: чанки, які можна процитувати одним посиланням.

| --- | --- | --- | --- | --- | --- | --- |
| структурний ≤ 1500, злиття < 200 | 2836 | 468 | 1163 | 3.9% | 0.0% | 67.2% |

Фіксовані вікна ріжуть кожен п'ятий пункт і в кожному четвертому чанку змішують два розділи чи дві статті, тож відповідь часто бачила б пів пункту або цитувала б не той. Структурні чанки ріжуть лише 3.9% одиниць, які лишаються довшими за 1500 символів навіть після поділу на підпункти, і ніколи не перетинають меж. Ця таблиця вимірює лише, де проходять межі; пошук виміряно в «Як працює пошук»: структурні чанки дають правильний текст у перших 5 для 0,93 питань, фіксовані вікна — для 0,73 (векторний пошук).

## Як працює пошук (етап 2)

`src/rag/search.py` шукає в індексі Qdrant, який будує `scripts/index_rag.py`; `scripts/eval_search.py` вимірює пошук на питаннях з відомою відповіддю. Код — `src/rag/bm25.py`, `embedding.py`, `index.py`, `search.py` і `search_eval.py`; тести — `tests/test_bm25.py`, `test_embedding.py`, `test_rag_index.py`, `test_index_rag.py`, `test_search.py`, `test_search_eval.py`, `test_eval_search.py`, усі на Qdrant у пам'яті й підставних моделях.

1. **Індекс.** Кожен чанк — одна точка Qdrant із двома векторами. `dense` — embedding bge-m3 (1024 числа, порівнюються косинусом) назви, розділу, заголовка й тексту чанка. `bm25` — ваги BM25 тих самих слів; на IDF їх множить сам Qdrant, тож новий документ не змінює ваг інших. Payload — увесь чанк, з індексами на `doc_id`, `doc_type`, `in_force` і `version_date` для фільтрів. Колекцій дві: `chunks` (2836 структурних чанків) і `chunks_fixed` (1278 вікон фіксованого розміру, базовий варіант).
2. **Застарілий індекс не використовується.** Після останньої точки колекція отримує штамп: хеш її чанків, модель, розмір вектора і версію індексу. Версію (`INDEX_VERSION` у `src/rag/index.py`) збільшують вручну щоразу, коли змінюється те, як чанк стає векторами (`searchable_text`, токенізатор, k1 і b для BM25): хеш чанків такої зміни не бачить. `Searcher` звіряє штамп один раз, коли його створюють, і зупиняється з «перебудуйте», якщо індекс зібрано з інших чанків, іншою моделлю чи іншою версією індексу або побудову не завершено.
3. **Embedder — bge-m3 через fastembed** (ONNX на CPU, без torch і без ключа). Знає українську, приймає до 8192 токенів, дає ті самі вектори, що bge-m3 в Ollama (косинус 0,9999 на чанках корпусу), і так само працює в GitHub Actions, де Ollama не підніметься.
4. **Три режими.** `vector`: косинус між питанням і кожним чанком. `hybrid`: 50 чанків за вектором і 50 за BM25, злиті через RRF (reciprocal rank fusion): чанк отримує бали за місця в обох списках, а не за їхні оцінки, які мають різні шкали. `hybrid_rerank`: перші 20 гібрида ще раз читає bge-reranker-v2-m3 (int8 ONNX) — cross-encoder, що читає питання й чанк разом; він краще оцінює пару, але надто повільний для всього індексу.
5. **Фільтри** (`SearchFilter`). `contract_id`: цей договір плюс усі закони й постанови, ніколи — інший договір; з `doc_types: [contract]` — лише цей договір. `doc_types`: лише ці типи. `skip_repealed`: відкидає закони, що втратили чинність (`in_force` є лише в законів, тож договори й постанови лишаються). `version_from` / `version_to`: дата є лише в постанов, тож чанки без дати проходять, а з датою мають потрапити в діапазон.
6. **Питання.** 15 у `data/rag/search_questions.yaml`, написав і перевірив автор: 7 про конкретний договір (own_003, own_008, prozorro_009), 6 про закон, 2 про постанови ВС; 4 `exact` (рідкісні слова чи числа, спільні з відповіддю), 5 `paraphrase` (те саме іншими словами), 6 `plain`. Знайдений чанк правильний, коли він з документа питання й дослівно містить його `evidence` (пробіли, переноси рядків і апострофи порівнюються нестрого), тож одне правило оцінює і структурні чанки, і фіксовані вікна. Тест звіряє кожне evidence з `chunks.jsonl`.
7. **Метрики.** R@k — частка питань із правильним чанком серед перших k. MRR — середнє 1/місце першого правильного чанка, промах (немає в перших 10) — 0; правильний чанк на 1-му місці важить більше, ніж на 5-му.

| пошук (06.11.2026, 15 питань, структурні чанки) | R@1 | R@3 | R@5 | R@10 | MRR | середній час, с |
| --- | --- | --- | --- | --- | --- | --- |
| vector | 0.67 | 0.93 | 0.93 | 0.93 | 0.79 | 0.03 |
| hybrid | 0.53 | 0.87 | 0.87 | 0.93 | 0.69 | 0.02 |
| hybrid + rerank | 0.73 | 0.93 | 0.93 | 0.93 | 0.81 | 1.99 |

| R@5 / MRR | vector | hybrid | hybrid + rerank |
| --- | --- | --- | --- |
| структурні чанки | 0.93 / 0.79 | 0.87 / 0.69 | 0.93 / 0.81 |
| фіксовані вікна | 0.73 / 0.72 | 0.80 / 0.70 | 0.87 / 0.79 |
| 7 питань про договір: лише цей договір | 1.00 / 1.00 | 1.00 / 0.93 | 1.00 / 1.00 |
| те саме, разом із законами й постановами | 1.00 / 0.64 | 1.00 / 0.61 | 1.00 / 0.72 |

Повний звіт, з recall за типом питання й місцем для кожного питання, — `results/stage2/search/2026-11-06T10-29-42/search_metrics.md`; кожен пошук із чанками, що прийшли замість правильного, — `ranks.jsonl` поруч.

Що кажуть цифри. Reranking дає найкращі R@1 і MRR, але простий векторний пошук відстає на одне питання за R@1 і працює в 66 разів швидше. На 15 питаннях одне питання — це 0,07, тож різниця в одне-два питання не вважається перевагою. Hybrid сам по собі тут гірший за vector: vector і так знаходить кожне `exact`-питання першим, тож BM25 нічого додати, а на `plain`-питаннях він піднімає чанки, де повторюються слова питання («Що таке пеня?» опускає визначення з 3-го місця на 6-те). Структурні чанки кращі за фіксовані вікна за R@5 у кожному режимі (за MRR у hybrid нічия: 0,69 і 0,70). Питання про договір утримує свій пункт у перших 5, коли дозволено закони й постанови, але втрачає перше місце через постанови, що цитують схожі пункти чужих договорів, тож питання про договір шукає лише в цьому договорі.

**Рішення, ухвалені на Е2.4.** Embedder — bge-m3 через fastembed (пункт 3), тож та сама модель працює локально й у CI. Qdrant локально працює в Docker (`docker-compose.yml`); тести використовують Qdrant у пам'яті, CI — service container (Е2.6). Кожен прогін оцінки йде в нову папку з назвою за часом початку, як на етапі 1.

**Відомі обмеження і що лишилось зробити:**

- **Фільтри.** Питання про договір шукають лише в договорі; пошук у договорі разом із законом та інші фільтри ще треба доробити (один із варіантів для етапу 3 — окремі інструменти агента «пошук у договорі» і «пошук у законі»).
- **Чия позиція в абзаці постанови.** q15 пропускає кожен режим, хоча кожен знаходить правильну постанову: він повертає абзаци з позицією апеляційного суду, яку Верховний Суд скасував. Усі абзаци постанови лежать в одному розділі «ВСТАНОВИВ:», тож чанк не знає, що в ньому — міркування нижчого суду чи висновок ВС. Бот процитував би скасовану позицію; постанови треба ділити за їхніми підрозділами або позначати, чия позиція в абзаці.
- **BM25 без стемінгу:** «пеня», «пеню» і «пені» для нього три різні слова.
- **15 питань** розрізняють режими лише за великої різниці; довірчих інтервалів поки немає.

## Як працюють відповіді (етап 2)

`scripts/ask_rag.py` ставить 26 питань із `data/rag/answer_questions.yaml` і записує кожну відповідь із джерелами в `results/stage2/answers/<час початку>/`. Код — `src/rag/context.py`, `answerer.py`, `answer.py`, `answer_config.py` і `answer_eval.py`; налаштування — `configs/answer.yaml`; тести — `tests/test_rag_context.py`, `test_rag_answerer.py`, `test_rag_answer.py`, `test_answer_config.py`, `test_answer_eval.py`, `test_ask_rag.py`.

1. **Три пошуки.** Договір із питання (4 чанки), закони (3) і постанови (3) шукаються окремо режимом `hybrid_rerank`, а потім чергуються: у спільному топі довгі постанови витісняли закони. В інших договорах пошуку немає ніколи.
2. **Поріг замість здогадки.** Чанк з оцінкою reranker нижче −1,7 — це шум. Якщо не лишилось нічого, відповідь — «У документах цього немає», модель не питаємо, тож це нічого не коштує.
3. **Контекст.** Цілі чанки, приблизно до 4000 токенів. Кожен чанк — блок `<document id="S1">` з назвою, типом, джерелом і попередженням. Усе, що в чанку чи питанні могло б закрити блок або відкрити підроблений, екранується: текст договору — це дані, а не інструкції.
4. **Відповідь.** Claude Haiku 5.5 заповнює обов'язковий інструмент `record_answer`: твердження, кожне з мітками своїх чанків, або `not_in_documents`. Невалідна відповідь один раз повертається з причиною; якщо й виправлення невалідне, результат — `failed`.
5. **Цитати й попередження пише Python.** Він перевіряє, що кожна мітка була в контексті, і будує цитату з метаданих чанка, тож цитата не може назвати пункт, якого в чанку немає; текст твердження все одно пише модель. Господарський кодекс не діє з 28.08.2025: його стаття отримує «ГК втратив чинність…», постанова, що на нього спирається, — «Це практика за ГК, що втратив чинність 28.08.2025.». Хибна відповідь моделі не може їх прибрати.
6. **Питання.** 15 питань пошуку і 11 пасток: 5 поза корпусом (t01, t02, t06–t08), 2 про скасований кодекс (t03, t04), 1 ін'єкція (t05) і 3 про договір із тим самим пунктом, але іншими числами (s01–s03). Прогони в таблиці нижче ставили перші 20 (q01–q15, t01–t05); t06–t08 і s01–s03 з'явилися разом із тестовим набором Е2.6. Дві перевірки не потребують судді: outcome такий, як очікували, і відповідь цитує чанк із доказом.

| --- | --- | --- | --- | --- | --- |
| v1 (`2026-11-07T20-17-50`) | 19 / 20 | 16 / 18 | 50 436 / 7 248 | 0.43 | 7.1 / 9.3 |
| v2 (`2026-11-08T17-24-00`) | 19 / 20 | 16 / 18 | 62 672 / 5 128 | 0.44 | 6.7 / 9.4 |

Два пропущені докази — q03 і q15. Відповіді також різняться від запуску до запуску, тому v2 і v3 порівняно за 4 спробами кожну, прочитавши всі відповіді вручну, і обрано v3 (`prompts/CHANGELOG.md`, «answer v3»). Пастки втрималися в усіх версіях.

**Відомі обмеження і що лишилось зробити:**

- **Доводи сторони подано як думку суду.** q05 і t03 повторюють ту саму помилку в кожній спробі: модель не відрізняє розділ із доводами скаржника від висновку суду. Промпт цього не виправив; код знає розділ, тож позначати або не брати такі чанки має він. Суддя теж це знаходить (q05, твердження 4).
- **Умови чужого договору.** Постанова може цитувати договір іншої сторони, а відповідь — повторити його умови (q01 у 3 з 4 спроб v3, t03 в усіх).
- **Чужі слова** («half») трапляються з правилом «лише українською» так само часто, як без нього, а Haiku 5.5 приймає лише семплінг за замовчуванням.
- **Поріг** підібрано на 23 питаннях, і він втрачає q03; його перерахуємо на тестовому наборі Е2.6.

## Як перевіряються відповіді (етап 2)

Збережений прогін відповідей перевіряють два скрипти; жоден не шукає й не потребує Qdrant, тож прогін можна перевірити знову будь-коли. Питання та їхні еталони — `data/rag/answer_questions.yaml`; пороги — `configs/eval.yaml` (правила) і `configs/judge.yaml` (суддя). Код — `src/rag/answer_scoring.py`, `src/rag/judge.py`, `scripts/score_answers.py`, `scripts/judge_answers.py` (калібрування судді — окремий підрозділ нижче); тести — `tests/test_answer_scoring.py`, `test_score_answers.py`, `test_judge.py`, `test_judge_answers.py`.

1. **Тестовий набір.** Кожне з 26 питань має еталонну відповідь, написану людиною (`expected_answer`), і ключові факти, які є в правильній відповіді (`key_facts`: число, основа слова, варіанти через `|`). Пастки зі схожим договором мають ще й заборонені факти: числа іншого договору. Кожен ключовий факт є в чанку з доказом, і тест стежить, щоб так і лишалося.
2. **Правила, безкоштовно.** `score_answers` шукає факти лише в твердженнях (цитати й попередження містять числа, яких модель не казала) і пише `scores.md`. П'ять порогів: правильне джерело ≥ 85%, ключові факти ≥ 80%, «У документах цього немає» на кожне питання поза корпусом, жодного забороненого факту, жодного твердження, що називає Господарський кодекс чинним.
3. **Суддя, Claude Sonnet 5.5.** Модель інша, ніж та, що відповідає, тож вона не оцінює власних звичок. Дві перевірки, по одному виклику:
   - **correct** — відповідь проти еталона: висновок, посилання й числа, три так/ні; відповідь правильна, коли всі три — так. Питання без відповіді — помилка, яка нічого не коштує. 5 питань поза корпусом лишаються правилам.
   - **faithful** — кожне твердження проти документів, які воно цитує, без еталона. Відповідь зберігає ці документи точно такими, якими їх прочитала модель (`cited_documents` в `answers.jsonl`), тож вердикт не залежить від сьогоднішнього `chunks.jsonl`. Прогін, збережений до цього, відхиляється ще до першого платного виклику.

   Вердикт — JSON за схемою (structured outputs): Sonnet 5.5 відхиляє обов'язковий виклик інструмента, яким користуються відповіді. Вердикт, якого Python не приймає, один раз повертається з причиною, а потім стає `failed`. Оцінка без вердикту рахується як промах, тож збій судді не може підняти результат. У сумнівному випадку суддя каже «ні»: фермер діє за цією відповіддю.
4. **Результати.** У папці прогону: `judge.jsonl` (кожен вердикт із поясненнями, модель, версія й хеш промпту, токени, latency) і `judge.md` (таблиця по питаннях і твердження без опори). `--limit N` оцінює лише перші N питань: перевірка, що суддя працює, без порогів.

Перший повний прогін, `2026-11-10T10-08-19` (промпт відповідей v3):

| перевірка | виміряно | поріг | пройдено |
| --- | --- | --- | --- |
| правила: цитує правильне джерело | 19 / 21 (90%) | ≥ 85% | ✓ |
| правила: ключові факти | 36 / 40 (90%) | ≥ 80% | ✓ |
| правила: «немає» на питання поза корпусом | 5 / 5 | усі | ✓ |
| правила: заборонені факти; ГК як чинний | 0; 0 | 0 | ✓ |
| суддя: correct | 19 / 21 (90%) | ≥ 80% | ✓ |
| суддя: faithful-твердження | 41 / 47 (87%) | ≥ 90% | ✗ |

Суддя коштував $0,19 за прогін (61 462 токени на вході, 6 936 на виході), близько $7,4 на 1000 питань; самі відповіді — $0,01.

Що кажуть вердикти, перечитані вручну за документами. Два промахи correct — q03 (без відповіді: його пункт нижче порогу) і s03 (п. 6.1 рахує 3 дні від переходу права власності й отримання документів; відповідь документи пропускає). Із 6 тверджень без опори чотири — справжні помилки: q01 і t05 розширюють п. 7.2 зі строків п. 6.2 і 6.4 до будь-якого строку договору, q05 подає довід скаржника як позицію Верховного Суду, t03 каже, що суд розглядав справу у 2014 році (це період договору; постанова — 2026 року). q11 — суворо, але обґрунтовано: відповідь додає «лише» до ст. 617 ЦК. q13 — наполовину: пропущене «або прийняття товаророзпорядчих документів» справжнє, але суддя ще й вимагає попередження про ГК усередині твердження — він не бачить попереджень, які Python додає під відповіддю (крок 5 у «Як працюють відповіді»).

### Калібрування судді на ручних оцінках

Суддю використовуємо, лише якщо він збігається з людиною. `scripts/judge_sheet.py` пише `data/rag/judge_marks.yaml`: 20 відповідей і 47 тверджень, які суддя оцінив у прогоні, кожне з питанням, еталоном, відповіддю й документами, які цитує твердження, але без вердиктів судді. Автор заповнює `correct` і кожне `supported` за правилами промптів судді (вони на початку аркуша). `scripts/calibrate_judge.py` ставить кожну оцінку поруч із вердиктом судді й пише `calibration.md` у папку прогону. Обидві перевірки потребують згоди ≥ 80% (`agreement_min` у `configs/judge.yaml`), інакше суддю не використовуємо; вердикт, якого суддя не дав, рахується як розбіжність. Код — `src/rag/calibration.py`; тести — `tests/test_calibration.py`, `test_judge_sheet.py`, `test_calibrate_judge.py`.

На 7 питаннях (q01, q05, q11, q13, t03, t05, s03) автор читав вердикти судді до розмітки. Вони лишаються в аркуші як `seen`: усі 6 тверджень, які суддя відхилив, і його єдиний correct ✗ — серед них, і без них згода нічого б не перевіряла. Тому згоду рахуємо по всіх відповідях і окремо по не бачених і бачених. t05 (ін'єкцію) перепозначено до порівняння: її `false` оцінював питання, а не відповідь, яка ін'єкції не піддалася.

Результати на прогоні `2026-11-10T10-08-19`:

| перевірка | усі | не бачені | бачені | поріг | пройдено |
| --- | --- | --- | --- | --- | --- |
| correct | 19 / 20 (95%) | 13 / 13 (100%) | 6 / 7 (86%) | ≥ 80% | ✓ |
| faithful | 40 / 47 (85%) | 27 / 28 (96%) | 13 / 19 (68%) | ≥ 80% | ✓ |

Суддя проходить, і його використовуємо. На сліпих оцінках він збігається майже завжди; на бачених автор частіше з ним не погоджувався, тож оцінки не йшли за його вердиктами. Із 8 розбіжностей 2 — «суддя так, автор ні», пропущена помилка (q01 твердження 2, q04 твердження 1), і 6 — «суддя ні, автор так», надто суворий суддя (q01 твердження 3, q05 твердження 4, q11 твердження 1, q13 твердження 2, t03 твердження 3, s03 correct). Перечитані за документами, щонайменше чотири з них — помилки автора, а не судді: q01 твердження 2 і q04 твердження 1 кажуть те, що кажуть п. 7.2 і п. 6.3; q01 твердження 3 розширює п. 7.2 так само, як t05 твердження 2, яке автор позначив false; t03 твердження 3 датує розгляд справи періодом договору. Оцінки не змінюємо після читання пояснень судді: тоді вони вже не були б сліпими.

**Що лишилось:** промпт faithful, який бачить попередження, що їх додає Python (q13).

## CI

GitHub Actions (`.github/workflows/ci.yml`) перевіряє кожен push і pull request, безкоштовно й без ключа: `uv sync --locked` (точно версії з `uv.lock`), `pytest`, `mypy`, правила на найновішому прогоні відповідей (`score_answers`, пороги з `configs/eval.yaml`) і калібрування судді (`calibrate_judge`, згода ≥ 80%). Непройдений поріг валить запуск. Тестам не потрібні ні Qdrant, ні моделі: Qdrant працює в пам'яті, embedder і reranker замінені підробками.

Платний суддя запускається лише вручну: Actions → CI → Run workflow (поле `limit` оцінює лише перші N питань). Йому потрібен секрет `ANTHROPIC_API_KEY` у Settings → Secrets and variables → Actions; його `judge.md` і `judge.jsonl` зберігаються як артефакт запуску. Доки немає промпту faithful, що бачить попередження, цей job падає: faithful 87% проти 90%.

Дії закріплені за хешем коміту (тег можна пересунути), checkout не зберігає токен GitHub, а workflow може лише читати репозиторій.
